# Virus scanner assessment — 2026-10-18

Scope: the Microsoft Defender clearance gate shared by Red Lotus Player and Walkman Bridge 0.4.1 at commit `6ffb9c9`: `backend/scan.py`, `backend/scan_bridge.py`, `backend/defender_status.py`, `backend/media_service.py`, the scanner routes and stream gating in `backend/application.py`, `electron/scanner-broker.cjs`, and the .NET helper under `scanner-helper/`. Method: direct source review plus the repository's own tests, executed in a Linux container. No Windows host, Defender, UAC, .NET SDK or Electron runtime was available, so every Defender interaction below was exercised through the suite's injected test seams, never against a real scanner. No production file was changed by this assessment.

## Question answered: are uploads and link downloads scanned automatically?

Yes. Both ingress paths already converge on the same mandatory scan before any decoding, playback, conversion or device write, with no operator action and no bypass switch.

| Ingress | Path through the code | Scan point |
| --- | --- | --- |
| File picker / drag-and-drop | `POST /api/media/import` (`application.py:307`) copies bytes into the managed cache, then `schedule()` runs `MediaService.run(kind='import')` as a background task | `run()` calls `clear_group(ids, 'source', job)` first (`media_service.py:272`); `clear()` invokes `scanner.scan_audio` (`media_service.py:57`) |
| Import link (YouTube / SoundCloud) | `POST /api/media/import-link` (`application.py:310`) runs `run_link_import`, which downloads opaque bytes, calls `store.import_file`, then hands the new media ID to the same `run(kind='import')` (`media_service.py:254`) | identical: `clear_group` before `prepare_metadata`, artwork extraction or conversion |

Consumption is gated independently of ingress: the stream route re-validates clearance against the file bytes on every request (`application.py:391`), artwork does the same (`application.py:338`), derivatives are scanned separately (`media_service.py:157`, `:174`), and the device write re-clears the transfer MP3 under the read lock (`media_service.py:337`). The link downloader forbids yt-dlp post-processing and fixups (`link_import.py:367`, `:436`), so no decoder touches downloaded bytes before Defender.

Existing tests pin this: `test_api.py::test_denied_clearance_never_reaches_decoder_or_device`, `test_media_upgrade.py::test_link_import_uses_scan_gate_and_keeps_provider_metadata` and `test_media_upgrade.py::test_link_download_never_decodes_when_defender_rejects`. All three pass here. No code change is needed to satisfy "scan on upload and on link download".

## Design strengths observed

- Fail-closed everywhere: missing, disabled, passive, timed out, errored, cancelled or ambiguous Defender outcomes never produce `ok`. Only exit 0 plus complete live signature status yields `CLEAN` (`scan.py:205`; helper `Protocol.cs:115`).
- Content binding: SHA-256 and size are captured before the scan, re-checked after it, re-checked by the helper on an open handle, and re-checked at every consumption. Clearance also binds policy version, 24-hour age and live engine/signature/platform versions (`scan.py:208`).
- Windows read lock: `locked_read` opens with share mode READ only, so neither writer nor delete/rename can race a scan or a stream (`media_store.py:82`).
- Elevation protocol: nonce, request identity, media ID, path, digest, size and helper PID are all bound; the kernel, not JSON, identifies the pipe peer on both ends (`SecurePipe.cs:27`, `:34`); results are validated as a whole batch before any clean result is forwarded (`scanner-broker.cjs:71`).
- Privileged helper hardening: fixed `MpCmdRun` arguments with `-DisableRemediation`, absolute OS PowerShell with module auto-loading disabled, runtime hooks/profilers stripped, startup-hook and debugger support compiled out (`ScannerHelper.csproj:9`).
- Main-only routes: the four `/api/internal/scanner/*` endpoints reject the renderer cookie and require the native header capability (`security.py:37`); the Electron source smoke asserts the renderer gets 403.

## Findings

Severity reflects impact on the scanner's security goal; every item below fails closed, so none grants clearance to unscanned bytes.

| # | Severity | Location | Finding | Recommendation |
| --- | --- | --- | --- | --- |
| 1 | Medium-low | `backend/scan.py:182-186` | The Python gate classifies a threat only by the English text regex `_THREAT`; `MpCmdRun` exit code 2 (Microsoft's documented "threats found" code) without matching text becomes `ERROR`/`defender_scan_error`, so the item shows **Failed** and is retryable rather than **Blocked**, and the `threats` counter is not incremented. The helper already treats exit 2 as a threat (`Protocol.cs:100`). On a non-English Windows a detected threat in an uploaded file would therefore be reported as a scan error. The regex is also DOTALL and matches a clean result when the user's profile path contains the word "threat" (probe: `Scanning C:\Users\Threat Lab\...\source.mp3 found no threats.` matches), mislabelling a clean file as a threat. | Treat exit code 2 as `defender_threat` regardless of text, as the helper does; restrict text matching to the "found N threats" form, or drop it. Update the `returncode=2, stdout='Scanning error'` case in `test_scan.py:108` accordingly. |
| 2 | Low | `backend/scan.py:314-346` | `_validate_id3` re-slices the remaining tag body on every frame (`body = body[header_size + frame_size:]`), which is quadratic in the tag size. Measured on this host with a 2 MiB ID3v2.3 tag of 190,557 minimal `TXXX` frames: 13.4 s of CPU before Defender is even invoked (64 KiB: 0.01 s, 1 MiB: 1.83 s). A 200-file import batch of such files would occupy the import worker for about 45 minutes. This parsing runs on untrusted bytes before the scan. | Walk the tag with an integer cursor instead of slicing; optionally cap the frame count. |
| 3 | Low | `backend/scan.py:270`, `:386`, `backend/media_store.py:21`, `frontend/src/App.jsx:197` | Format-gate false positives: ID3v2.3 tags with the unsynchronisation flag, MP3s with padding or junk between the tag and the first frame, and tag-size mismatches are all `BLOCKED` as `invalid_audio_format`. The picker offers `.opus`, `.wma`, `.aif`, `.aiff`, but `MIMES` lacks them, so they are stored as `source.bin` and always rejected (`.opus` is in `_EXT_FAMILY` but not in `MIMES`). Conversely `.mp4` video containers pass the audio gate because the check is container-level. | Align the picker with `MIMES`; either support unsynchronised ID3v2.3 or document the rejection; consider a probe-after-clearance step rather than a stricter pre-scan parser. |
| 4 | Low (acknowledged by the 2026-09-05 review) | `electron-builder.yml:13`, `:19`, `NativeExchange.cs:22-30` | The products install per user (`perMachine: false`, `asInvoker`) and the unsigned `RedLotus.ScanHelper.exe` is launched with `runas`. Any process running as the same user can replace the helper on disk and ride the application's legitimate UAC prompt to administrator. The prompt also shows an unknown publisher, which conditions users to approve unsigned elevation. | Before public release: Authenticode-sign the helper and install it to an administrator-only location (per-machine install for the helper, or a per-machine helper package). Signature verification by the unelevated exchange is not sufficient on its own since the exchange is equally replaceable. |
| 5 | Low (availability) | `SecurePipe.cs:17-22` | The elevated pipe ACL grants only the elevated token's own SID plus Administrators. When a standard user elevates with a different administrator's credentials, the unelevated exchange client runs as the standard user and cannot connect, so every elevation fails closed (`elevation_failed`) and files needing elevation can never be cleared on that account type. | Resolve the client SID from the `--expected-client-pid` process token inside the elevated helper and grant that SID instead of `WindowsIdentity.GetCurrent()`. |
| 6 | Low | `backend/media_service.py:77-97`, `backend/media_store.py:293` | With `-DisableRemediation`, a file Defender reports as a threat is not quarantined by the scan; the managed copy stays in `%LOCALAPPDATA%` as a `blocked` queue item until the user removes it. Real-time protection may act independently, but the application keeps known-bad bytes on disk by design. | Delete the managed bytes of `THREAT`/`BLOCKED` outcomes immediately while keeping the record and reason for display. |
| 7 | Very low | `backend/scan.py:409`, `DefenderScanner.cs:27` | Platform-folder fallback picks `MpCmdRun.exe` by lexicographic folder order while `_query_defender_registry_status` orders numerically (`scan.py:502`). When two same-month revisions coexist (probe: `4.18.25080.5-0` vs `4.18.25080.11-0`) the executable chosen is the older revision while the reported platform version is the newer one. The primary `Program Files` candidate normally wins first, so this only affects the fallback. | Reuse `_version_key` (and an equivalent in C#) for the fallback ordering. |
| 8 | Informational | `backend/application.py:391`, `backend/scan.py:208` | Every stream request, including each HTTP range request issued by the media element while seeking, re-hashes the full file (up to 500 MiB) and re-queries Windows Security Center plus the registry and the service manager. This is the intended re-verification, but it is a measurable per-seek latency on large WAV files. | If needed, cache the digest per open read lock (the share-mode lock already guarantees the bytes cannot change while held) and cache the status query for a few seconds. |

## Limits

This is a bounded source review with test execution on a non-Windows host. It does not establish behaviour across Windows editions or Defender configurations, does not cover the Java device engine, and makes no claim about installer or code-signing status beyond what the configuration files state. The 2026-09-05 review's release gates (signing, clean-machine acceptance, physical device verification) remain open.
